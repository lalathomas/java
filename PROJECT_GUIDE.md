# Project Guide and Home Transfer Instructions

This document explains the generated Wallet Ledger project, especially `pom.xml`, the source-code layout, infrastructure files, tests, and how to transfer the project to another computer through GitHub.

For the product design, API examples, concurrency strategy, and limitations, also read [`README.md`](README.md).

## 1. What is transferred through Git

The Git repository contains everything needed to rebuild the service:

- Java source code
- Maven build configuration
- Flyway database migration
- application configuration
- automated tests
- Dockerfile and Docker Compose configuration
- CI workflow
- README and this guide

The following local files are intentionally **not** transferred:

| Local item | Why it is excluded |
|---|---|
| `target/` | Generated by Maven; rebuild it with `mvn clean verify` |
| `*.pdf` | Prevents the confidential assignment PDF from being published |
| `.env` and `.env.*` | May contain local credentials or secrets; `.env.example` is allowed |
| `.idea/`, `.vscode/`, and IDE files | Machine-specific editor settings |
| logs and local H2 files | Generated runtime/test data |

The ignore rules are in [`.gitignore`](.gitignore). The PDF stays on this work computer but is not included in the Git commit.

## 2. Maven configuration: `pom.xml`

Maven reads [`pom.xml`](pom.xml) to determine the Java version, framework version, dependencies, plugins, tests, and output artifact.

### 2.1 Project identity

```xml
<groupId>io.github.lalathomas</groupId>
<artifactId>wallet-ledger-service</artifactId>
<version>0.0.1-SNAPSHOT</version>
```

- `groupId` is the Java/Maven namespace and matches the GitHub account naming convention.
- `artifactId` is the project and generated JAR name.
- `SNAPSHOT` means this is still a development build rather than a published final release.

The packaged application is generated as:

```text
target/wallet-ledger-service.jar
```

### 2.2 Spring Boot parent

```xml
<parent>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-parent</artifactId>
    <version>3.5.15</version>
</parent>
```

The Spring Boot parent supplies compatible dependency and Maven-plugin versions. This avoids manually selecting versions for Spring MVC, Hibernate, Jackson, JUnit, Testcontainers, and related libraries.

### 2.3 Java version

```xml
<java.version>17</java.version>
```

The compiler targets Java 17, which is the minimum version required by the assignment and Spring Boot 3.x.

### 2.4 Runtime dependencies

| Dependency | Why it exists |
|---|---|
| `spring-boot-starter-web` | REST controllers, JSON serialization, embedded web server, and HTTP error handling |
| `spring-boot-starter-validation` | `@Valid`, `@NotNull`, `@Positive`, `@NotBlank`, and request constraints |
| `spring-boot-starter-data-jpa` | JPA entities, repositories, transactions, Hibernate, and pessimistic row locking |
| `flyway-core` | Applies versioned SQL database migrations during startup |
| `flyway-database-postgresql` | PostgreSQL-specific Flyway support |
| `postgresql` | PostgreSQL JDBC driver used by the running application |

The PostgreSQL driver is `runtime` scope because application code compiles against standard JDBC/JPA APIs rather than driver classes.

### 2.5 Test dependencies

| Dependency | Why it exists |
|---|---|
| `spring-boot-starter-test` | JUnit 5, AssertJ, Mockito, Spring integration testing, and MockMvc support |
| `h2` | Fast portable integration database used by the default local test suite |
| `spring-boot-testcontainers` | Connects Spring Boot automatically to a test container through `@ServiceConnection` |
| `testcontainers-junit-jupiter` | Starts/stops containers through JUnit 5 |
| `testcontainers-postgresql` | Runs the concurrency suite against the real production database engine |

All test dependencies have `test` scope, so they are not packaged into the production JAR.

### 2.6 Build plugins

#### Spring Boot Maven plugin

Repackages the normal JAR into an executable JAR containing the application and runtime dependencies:

```powershell
java -jar target/wallet-ledger-service.jar
```

#### Maven Enforcer plugin

The enforcer rejects unsupported build environments:

- Java must be 17 or newer.
- Maven must be 3.9 or newer.

This catches the common Windows problem where `java -version` reports Java 17 but Maven still uses an old `JAVA_HOME` pointing to Java 8.

### 2.7 Common Maven commands

```powershell
# Compile production code
mvn compile

# Run all locally available tests
mvn test

# Clean, test, verify, and package
mvn clean verify

# Run one test class
mvn -Dtest=WalletServiceIntegrationTest test

# Run the application locally
mvn spring-boot:run
```

## 4. Production source-code layout

All Java source is below:

```text
src/main/java/io/github/lalathomas/walletledger/
```

### 4.1 Application entry point

| File | Purpose |
|---|---|
| `WalletLedgerApplication.java` | Starts Spring Boot and component scanning |

### 4.2 HTTP/API layer: `wallet/api`

| File | Purpose |
|---|---|
| `WalletController.java` | Defines create, credit, debit, refund, balance, and history endpoints |
| `CreateWalletRequest.java` | Validates the player ID when creating a wallet |
| `MoneyMovementRequest.java` | Validates amount, reason, and reference before creating an application command |
| `RefundRequest.java` | Validates refund reason/reference; the amount is derived from the original debit |
| `WalletResponse.java` | Wallet-creation response |
| `BalanceResponse.java` | Current-balance response |
| `MoneyMovementResponse.java` | Credit/debit/refund result, including transaction ID, reversal link, and replay status |
| `TransactionResponse.java` | One public ledger-history item |
| `TransactionHistoryResponse.java` | History list plus pagination metadata |

JPA entities are never returned directly from this layer. HTTP DTOs keep database details out of the public contract.

### 4.3 Application layer: `wallet/application`

| File | Purpose |
|---|---|
| `WalletService.java` | Core use cases, transaction boundaries, row locking, validation, idempotency, refunds, and mappings |
| `MoneyMovementCommand.java` | Internal normalized credit/debit input |
| `RefundCommand.java` | Internal normalized refund input |
| `MoneyMovementResult.java` | Internal result for a successful/replayed mutation |
| `WalletSnapshot.java` | Internal projection of current wallet state |
| `LedgerEntryView.java` | Internal history projection |
| `TransactionHistory.java` | Internal paginated history result |
| `WalletException.java` | Domain/application exception with safe structured details |
| `WalletErrorCode.java` | Stable machine-readable error codes |

`WalletService` is the most important file to understand before an interview or code review.

### 4.4 Domain layer: `wallet/domain`

| File | Purpose |
|---|---|
| `Wallet.java` | Wallet entity, exact `long` arithmetic, and non-negative balance invariant |
| `LedgerEntry.java` | Immutable successful balance-change record, including refund-to-debit linkage |
| `TransactionType.java` | `CREDIT`, `DEBIT`, and `REFUND` enum |

### 4.5 Persistence layer: `wallet/persistence`

| File | Purpose |
|---|---|
| `WalletRepository.java` | Wallet lookup, creation, and `PESSIMISTIC_WRITE` lock query |
| `LedgerEntryRepository.java` | Ledger insert, idempotency lookup, and deterministic history query |

The ledger repository intentionally exposes no update or delete operation.

### 4.6 Shared API errors: `common/api`

| File | Purpose |
|---|---|
| `ApiErrorResponse.java` | Consistent JSON error structure |
| `GlobalExceptionHandler.java` | Maps validation, domain, lock, database, and unexpected failures to HTTP responses |

## 5. Resource and database files

### `src/main/resources/application.yml`

Defines:

- PostgreSQL datasource defaults and environment-variable overrides
- Hikari connection-pool limits
- a five-second PostgreSQL row-lock timeout
- Flyway startup migrations
- Hibernate schema validation rather than schema creation
- UTC JDBC timestamps
- strict Jackson integer handling, so a decimal such as `1.9` is rejected rather than truncated to `1`
- graceful shutdown and safe error defaults

### `src/main/resources/db/migration/V1__create_wallet_ledger.sql`

Creates:

- `wallets`
- `ledger_entries`
- unique player-wallet constraint
- wallet-scoped idempotency constraint
- positive-amount and non-negative-balance checks
- transaction-type and nonblank audit checks
- restricted wallet deletion when history exists
- history lookup index

Flyway records migration version `1` and prevents accidental schema drift.

### `src/main/resources/db/migration/V2__add_transaction_refunds.sql`

Adds the optional transaction-refund model:

- `REFUND` ledger transaction type
- immutable `reversal_of_entry_id` link to the original debit
- unique source constraint preventing double refunds
- foreign-key and shape checks for linked refund entries

## 6. Automated tests

### `WalletServiceIntegrationTest.java`

Covers normal money paths and pressure cases:

- create/duplicate wallet
- credit and debit
- insufficient funds
- invalid input and missing wallet
- sequential duplicate replay
- idempotency conflict
- overflow
- pagination
- concurrent credits
- concurrent debits
- concurrent duplicate submissions
- refund success/replay and refund business-rule failures
- concurrent distinct-key refund attempts

### `WalletApiIntegrationTest.java`

Uses MockMvc to verify the real HTTP contract:

- endpoints and status codes
- replay header and response
- body/path/header validation
- malformed JSON
- strict decimal rejection with no balance change
- domain error details
- history response
- refund response linkage, replay, validation, and business errors

### `WalletTransactionRollbackIntegrationTest.java`

Forces the ledger repository to fail **after** the wallet entity has been changed, then proves the database transaction rolls the wallet balance back to its previous value.

### `PostgresWalletConcurrencyIntegrationTest.java`

Runs the highest-risk concurrent debit, duplicate-delivery, lock-timeout/retry, distinct-key refund, and same-key duplicate refund cases against an actual PostgreSQL container. It skips locally when Docker is stopped, but the GitHub Actions workflow fails if this test is skipped in CI.

### Test profiles

- `src/test/resources/application-test.yml` uses in-memory H2 and H2-compatible lock-timeout syntax for portable tests.
- `src/test/resources/application-postgres-test.yml` keeps the real PostgreSQL Testcontainer profile separate and uses PostgreSQL lock-timeout syntax.

## 7. End-to-end request flow

A credit, debit, or refund request follows this path:

```text
HTTP request
  -> WalletController
  -> request DTO validation
  -> MoneyMovementCommand or RefundCommand
  -> WalletService @Transactional method
  -> SELECT wallet FOR UPDATE
  -> idempotency lookup after lock
  -> funds/overflow validation
  -> Wallet balance mutation
  -> immutable LedgerEntry insert
  -> commit both changes or roll back both
  -> response DTO
```

The idempotency lookup occurs after the wallet lock. Therefore, when two identical requests arrive together, the second waits, sees the first committed transaction, and replays it without changing the balance again.

## 8. Transfer the project to your home computer

The project is published to this configured remote:

```text
https://github.com/lalathomas/java.git
```

The safe working branch used for this initial publication is:

```text
wallet-ledger-takehome
```

### 8.1 Clone directly at home

Install Git, JDK 17+, Maven 3.9+, and Docker Desktop. Then run:

```powershell
git clone --branch wallet-ledger-takehome --single-branch https://github.com/lalathomas/java.git
Set-Location java
```

If the repository is private, GitHub will require authentication. Use Git Credential Manager, a personal access token through the credential prompt, or SSH configured on your home computer. Never place a token inside a Git command, file, or remote URL.

### 8.2 Verify Java used by Maven

```powershell
java -version
mvn -version
```

If Maven still reports Java 8:

```powershell
$env:JAVA_HOME = "C:\Program Files\Java\jdk-17"
$env:Path = "$env:JAVA_HOME\bin;$env:Path"
mvn -version
```

### 8.3 Rebuild everything at home

```powershell
mvn clean verify
```

With Docker Desktop running, the PostgreSQL Testcontainers test should execute. Then start the service:

```powershell
docker compose up --build
```

The API will be available at:

```text
http://localhost:8080
```

### 8.4 Continue work from both computers

Before starting work on either computer:

```powershell
git switch wallet-ledger-takehome
git pull --ff-only
```

After making a small, reviewed change:

```powershell
git status
git add path/to/changed-file
git commit -m "Describe the change"
git push
```

Prefer adding specific files rather than `git add .`, especially when working near local documents or secrets.

## 9. Files to read first

To understand the project instead of only running it, read in this order:

1. `README.md`
2. `PROJECT_GUIDE.md`
3. `pom.xml`
4. `src/main/resources/db/migration/` (`V1` then `V2`)
5. `Wallet.java`
6. `LedgerEntry.java`
7. `WalletService.java`
8. `WalletRepository.java`
9. `WalletController.java`
10. `WalletServiceIntegrationTest.java`
11. `WalletTransactionRollbackIntegrationTest.java`
12. `PostgresWalletConcurrencyIntegrationTest.java`

After that sequence, you should be able to explain the data model, why the lock comes before the idempotency lookup, why balance and ledger commit together, and how the concurrent tests prove the wallet cannot overdraw.
